# Assignment A4: Verification and portfolio

Add house rule R8 (soft delete respected on every endpoint) to the shipharness check framework,
add a sixth test filter to the filter pipeline, run filtered test generation on a repository you
choose and pass its kept tests through your filter 6, run one live A/B on feature F4, and publish
the evidence: the live run files, an evidence report, a LangSmith page with the A/B's trace
links, a one-page case study, and a skill of your own. Sized for 3 to 6 hours (brief §5.1). Source
ids such as (A1, F-a-96) point to the research register in `RESEARCH.md` and `research/notes/`.

## Objective

Show that you can turn a written rule into a mechanical check that a referee can trust, extend the
test filter pipeline with a filter that has a clear reason to exist, and present verification
results so that a reader can check them.

## Problem statement

TeamTrack's handbook says: "Deleting an issue is a soft delete: it sets `deleted_at`, and deleted
issues behave as if they do not exist (404 on read, hidden from lists)"
(`teamtrack/docs/HANDBOOK.md`). Rules R1-R7 have checks; this one does not. An agent that adds an
endpoint can read the `issues` table without the `deleted_at` filter, and every visible test still
passes, because no visible test deletes an issue first. The legacy `/v1/issues` handler already
lists deleted issues today.

At the same time, `shipharness testgen` keeps a generated test when it passes filters 1-5, so two
generated tests that check the same thing in the same way are both kept. Nothing removes copies.

## Background

- House rules. "House rules" is the course label for what A1 calls "golden principles" encoded in
  the repository (A1, F-a-99) and "taste invariants" enforced "with custom lints" (A1, F-a-96;
  RESEARCH G-9). A1's reason to write them as code: "When documentation falls short, we promote
  the rule into code" (A1, F-a-43). Its advice for the messages: "we write the error messages to
  inject remediation instructions into agent context" (A1, F-a-97).
- Why a check must find what visible tests miss. SpecBench reports that "while every frontier agent
  saturates the visible suite, reward hacking persists, with smaller models exhibiting larger gaps
  on holdout suites" (B13, F-b-45). A4 sets the bar for the verifier: "it’s important that the
  task verifier is nearly perfect, otherwise Claude will solve the wrong problem" (A4, F-a-127).
  Your check is graded the same way: against seeded violations you do not see.
- Baselines. Every shipharness check reports new violations relative to the checkpoint baseline,
  so the legacy `/v1/issues` violation does not count against an arm unless the arm makes it worse
  (DESIGN §5, course mechanism). This works only if a finding's identity, `(rule, endpoint,
  severity, detail_key)`, is the same on every run (`src/shipharness/checks/base.py`,
  `mark_baseline`).
- Test filters. TestGen-LLM applies "a series of progressively demanding semantic filters to
  candidate solutions generated by the language models" (B11, F-b-16). Filters 1-3 in shipharness
  come from B11 and B12; filters 4 and 5 are course filters (DESIGN §7, RESEARCH G-7). Later
  TestGen-LLM versions "included an extra filter to remove previously seen test cases" (B11,
  F-b-26), based on syntactic equality of test bodies (RESEARCH correction 6). Your filter 6 follows
  that idea; ignoring renamed local variables is a course addition.
- Skills. A skill is a folder whose `SKILL.md` "must contain YAML frontmatter followed by Markdown
  content" (B1, F-b-01); `name` "Must match the parent directory name" (B1, F-b-02).
- Live step (course design). Grading runs offline so that scores are reproducible: R8 and filter 6
  are graded on seeded builds and candidate tests, never by calling a model. The live step adds
  one run of each model-backed command with the course model (`gpt-6-luna`), the real runner and
  sandbox, and the class cost caps. The grader validates the files those runs wrote; it does not
  re-run them and needs no keys.

## Detailed requirements

R8 check (`r8_soft_delete`, rule `R8`):

1. Discover endpoints with `open_target` (it calls `discover_endpoints` on the app's OpenAPI
   schema). Do not list endpoints by hand.
2. Soft-delete through the adapter before probing. The first id returned is the one path and body
   probes use. A response contains a deleted issue when it contains that issue's marker text.
3. An endpoint addresses one issue when its path has `{issue_id}`, or a parameter without a
   resource name (such as `{id}`) whose closest literal segment before it is `issues`.
   `{project_id}`, `{user_id}`, and other `*_id` names never address an issue.
4. Probe every endpoint as the home org's admin, lists first:
   - `deleted_list`: every GET endpoint that does not address one issue (path from the adapter's
     ids, required query parameters from `t.payloads.query`). Fails when the status is 2xx and the
     body contains a deleted issue's marker.
   - `deleted_body`: every write endpoint that does not address one issue and whose generated body
     has an `issue_id` key, sent with the deleted id. Fails when the status is 2xx.
   - `deleted_path`: every endpoint, any method, that addresses one issue, called with the deleted
     id (other parameters from the adapter's ids, body from `t.body`). Fails unless the status is
     404.
5. Each failure is one `Finding` with `rule="R8"`, `endpoint` set to the endpoint's label (for
   example `GET /issues/{issue_id}`), `detail_key` set to exactly the probe kind above, severity
   `leak` when a 2xx body contains a marker and `violation` otherwise, and a one-line `detail` that
   says what to change.
6. A numeric id alone is not evidence: project 1, user 1, and org 1 share the deleted issue's id.
7. Pass the findings through `apply_exemptions(findings, ctx)` and build the result with
   `make_result`; report progress with `ctx.progress`. Never call a model.
8. On TeamTrack as shipped, the only counted finding is `GET /v1/issues` with `deleted_list`.

Filter 6 (`NoDuplicateTest`):

1. The constructor takes the existing suite's tests as `CandidateTest`s (for example from
   `shipharness.filters.collect_candidates`). `evaluate` reads source only; it never runs a test.
2. Two tests are duplicates when their decorators, parameter lists, and bodies are equal as syntax
   trees after ignoring the function name, comments, and layout, dropping a docstring, and renaming
   every local variable (a name bound in the body by `=`, `+=`, annotated assignment, `for`,
   `with ... as`, `:=`, a comprehension, or `except ... as`) to a placeholder in order of first
   appearance. Parameters, globals, imported names, attribute names, and literals keep their names
   and values.
3. Discard a candidate that duplicates an existing test (other than one with the same test id) or a
   candidate this instance kept earlier, and name that test's id in the reason. Discard, with a
   reason, a candidate whose file does not parse or has no such function. Keep anything else.
4. Every result has `filter=6`, the candidate's `test_id`, and a non-empty reason.

## Common mistakes

- Matching deleted issues by numeric id. Project 1 and user 1 share the id, so lists of projects
  become findings.
- Probing only GET endpoints. A write that resolves a deleted issue (transition, assign) is the same
  violation.
- Hard-coding endpoint paths. The check must cover endpoints that exist only in the build.
- Missing `{id}` parameters: the resource comes from the segment before the parameter.
- Putting a random value or response text in `detail_key`. Findings then never match the baseline,
  and the legacy finding counts against every arm.
- Comparing tests as text. Formatting and comments change the text, not the test.
- Renaming fixture parameters in filter 6. `client` and `admin_client` are different fixtures.
- Pasting estimated numbers into the portfolio. Only output you ran counts.
- Running `apply_filter` without `--update-report`, or copying the report before running it. The
  report then has no filter-6 rows.
- Copying score records from another A/B, or a replay (`recorded` true). The grader matches the
  records to the `ab_id` that `live/ab.txt` printed.
- Editing a transcript. The run id, kept count, statuses, and costs are checked against the JSON
  files.
