# F3 Idempotency keys on issue creation

Status: planned. Section S3 (build phase, then a test phase).

## Goal

Clients that retry `POST /projects/{project_id}/issues` after a timeout never create duplicate
issues. This closes the roadmap item in HANDBOOK house rule R4.

## API

`POST /projects/{project_id}/issues` accepts the `Idempotency-Key` header with the semantics of house
rule R4, using `services.idempotency.run_once` (see `POST /projects` for the pattern).

- The same key with the same body returns the first response: status 201 and the same body,
  including the same issue id. Nothing new is created.
- The same key with a different body gives 409 `idempotency_conflict`; nothing is created.
- A key is scoped per org and per endpoint, and the endpoint is the request path: the same key used by
  another org, on `POST /projects`, or on another project's issue path is a new request.
- A replay adds no audit row. The first request adds one `issue.create` row, as before.
- Without the header every request creates an issue, as before.
- Only successful creates are remembered: a request that failed (403, 404, 422) does not use up the
  key.
- Checks run in the existing order: a viewer gets 403 and another org's project gives 404, with or
  without a key.

## Scope

- Change only the issue endpoint and its service (`app/api/issues.py`, `app/services/issues.py`) and
  tests. `app/api/middleware.py` is shared infrastructure and is out of scope (HANDBOOK "Code
  layout").
- In the test phase, add tests only (`tests/visible/`); do not change application code.

## Out of scope

Key expiry, idempotency for other endpoints.
